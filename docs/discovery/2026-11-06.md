## Product hypothesis

Daniel is the initial target user: an iPhone songwriter/poet who needs to retain a fleeting line or melody, then return and develop it with simple backing and takes. The sample provides a useful starting point. The core journey is capture → develop with backing → record → save → reopen → continue. Personal usefulness is the success criterion before distribution or revenue.

Hypotheses to test: capture is fast enough in the real creative moment; accompaniment helps rather than distracts; saved takes remain discoverable; returning to an idea is easier than using existing tools. These are hypotheses, not interview findings.

## Security/privacy assessment (initial, not a certification)

Assets: unpublished words and voice recordings, backup files and hosting account access. Boundaries: imported JSON/audio → model → rendered DOM; browser → persistent storage; browser → hosting/auth; optional speech recognition and font requests.

- Tampering/XSS: titles, lyric previews and take names are escaped; import regenerates identifiers, constrains chords/tempo and rejects non-data audio URLs. Tests exercise escaping and some invalid import. No exhaustive malicious-fixture audit yet.
- Disclosure: local storage and exported JSON are not application-encrypted; hosted access gate does not encrypt browser data. Browser speech recognition needs provider/privacy investigation before describing dictation as local. No app analytics or external AI processing found.
- Denial of service: import has a 250 MB file cap, imported clips 50 MB; JSON/base64 decoding still happens in memory. Oversized object/count abuse needs bounded tests.
- Spoofing/elevation: hosting account supplies access; no application account/backend endpoints in this repository. Preserve existing audience.
- Repudiation: no persistent audit trail. Prefer useful local save/recovery diagnostics without collecting creative content.
- Dependencies: no npm runtime/dev dependencies or install/build step. No lockfile-based npm vulnerability audit was run (no dependency graph). Actions checkout/setup-node use version tags; supply-chain hardening remains to assess. No dedicated history secrets scanner or production-header audit completed.

## Architecture checkpoint — provisional recommendation

Improve incrementally first. Keep the existing app as a baseline while proving persistence, recording and backups. Static web + IndexedDB has low operational cost and preserves continuity. Extract storage/audio modules only in small reviewed changes with behaviour tests.

Alternatives still open: PWA caching for offline entry; separate capture/stems for editable takes; authenticated cloud backup/sync with conflict and ownership design; native/wrapper capture if real background recording is essential. None is selected. A framework rewrite alone would not establish reliable iPhone audio behaviour.
